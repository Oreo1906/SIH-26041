# Offline session completion

`TrainingSessionService` owns practice/assessment progression, question selection,
score blending, demo certificate issuance, refresher creation and transactional
completion. UI and renderers do not reproduce the persistence workflow. It uses
no HTTP client or remote asset, authentication, signing or verification service.

Bundled `session-options.json` configures practice prerequisite and question count
(five for assessment). The banks contain eight questions each. A critical failure
ends the scenario, then still measures knowledge; the configured critical-fail
rule prevents a certificate regardless of quiz answers. Abandoned sessions do
not create a completed attempt. Storage retries preserve all UUIDs and timestamps.

Prototype provisioning is generated by `scripts/provision_demo_issuer.py` using
the backend virtual environment. It preserves ignored private keys in `.private`;
the public trust bundle is root-signed. The encrypted demo bootstrap includes its
wrapping key in the APK and is recoverable. This is the explicitly labeled docs08
demo fallback, not production key security. Android imports and rewraps the seed
in Android Keystore for device-local storage. The root private key is never bundled.
Rebuilds must retain the issuer identity; lost or mismatched device keys are not
silently replaced. Production provisioning remains a separate release requirement.

Verified in Unity EditMode: both modules complete practice and assessment, save a
signed certificate and policy-derived refresher, survive SQLite reopen and verify
locally. Duplicate completion does not enqueue duplicates. Unknown/duplicate answer
IDs are rejected; critical failure never issues a certificate. Android device
verification is separate and remains pending until evidenced in STATUS.md.

## Micro-training and reminders

Bundled micro-training mappings select up to two existing scenario steps from
ranked weak topics, preserving their original procedure order, text, actions and
critical-fail rules. A configured two-step general subset is used without weak
topics. Correct step scores normalize equally to 100 for the short scenario;
module scenario/quiz blending stays unchanged. Three questions prioritize the
record's weak tags. Subset scenario IDs are deterministic semantic IDs derived
from the parent scenario and selected step IDs. No safety threshold is added.

A passed refresher atomically appends its attempt, marks its source reminder
completed, and creates the next policy-derived due date and outbox records.
Refresher attempts do not issue new certificates (no policy authorizes that).
A failed refresher leaves the source reminder pending. Original certificates and
attempts remain append-only. Completion retries cannot duplicate these effects.

Opt-in Android reminders use a local inexact AlarmManager alarm and a generic
notification without worker identity. Permission is requested from Settings only.
Reboot/package-update receivers reschedule stored alarms. Due items always remain
visible in-app; Android battery policy may delay notifications. No exact-alarm
permission, remote push provider or background network connection is required.
See [Android alarms](https://developer.android.com/develop/background-work/services/alarms)
and [notification permissions](https://developer.android.com/develop/ui/compose/notifications/notification-permission).

QR scanning uses local camera frames and ZXing; no images are stored or uploaded.
The camera permission is requested only after Scan is tapped; navigation/background
stops the camera. Paste verification also works offline when camera access is denied.
